# VCL06 整机 ROS 节点话题拓扑与接口清理复核

## 1. 结论

正式链的视觉/导航核心口径已经收敛，但整机运行面尚不能称为“冗余接口全部清理完毕”。

- 已清理：正式入口无 `detect_compat_bridge`、无 `coverage_search_manager`，也没有注册旧
  landing/search/class/tank 控制及结果话题；导航直接消费 typed
  `/uav_vision/detections_mapped`。
- 已收口：`/fastplanner/goal` 只有 `/navigation/planner_bridge` 一个发布者。
- 合理保留：`/detect/point_class` 虽沿用旧名字，但当前有一个生产者、三个真实消费者；直接改名
  只会新增兼容层，当前不应动。`/Servo` 与 `/legacy/Servo_raw` 是受保护服务调用链，不是话题桥。
- 尚未清理：`patrol_control` 仍注册三个无人订阅的旧舵机控制话题 `/control1~3`，同时订阅无人
  发布的 `/servo/complete`。它们已被服务 ACK 路径取代，是本轮唯一导致接口审计 FAIL 的明确
  旧合同残留，归导航/控制侧源码所有。
- 启动面仍可减：正式 external/headless 链仍启动无人消费其输出的 `waypoint_generator`，以及
  RViz 关闭时只提供可视化输出的 `static_pointcloud_viz`。两者不是跨组接口冲突，但不应出现在
  最终精简运行入口。

因此，视觉侧旧桥清理已完成；整机侧还差导航/控制侧 4 个旧执行话题和 2 个按模式关闭的辅助
节点。无需新增消息、coordinator 或兼容桥。

## 4. 不应按“无人订阅”直接删除的接口

运行快照中的 one-sided topic 不等于全部冗余：

- MAVROS 会注册完整插件 API，部分接口等待 QGC、遥控器或外部诊断工具，不能仅因本轮无消费就删。
- `/uav_vision/perf`、视觉 debug 输出、FreeDOM/Planner 可视化输出属于观测面；debug/RViz 关闭时
  没有订阅者是正常现象。后续可按参数停止计算或发布，但不需要再造替代接口。
- `/mission/visual_delivery_audit_status` 等状态口本来就是供外部观测，运行内无订阅者并不构成
  无意义桥接。
- `/planning/pos_cmd` 及轨迹可视化口属于 Fast-Planner 内部/观测面，本轮不凭单次拓扑快照改动
  规划器合同。

## 5. 最小收口动作

导航/控制侧下一提交只做减法，并保留显式 2025 legacy 回归入口：

1. `patrol_control` 在 external mission mode 下不订阅 `/servo/complete`、不 advertise/publish
   `/control1~3`；legacy mode 维持原行为。现有 `/Servo` 服务许可链不变。
2. 给 PX4 planner launch 增加 `start_waypoint_generator`，正式 VCL06 external 入口传 `false`；
   legacy/manual RViz 入口仍可传 `true`。
3. 将 `enable_static_pointcloud_viz` 透传到完整 launch，正式 `rviz=false` 时设为 `false`；FAST-LIO
   → FreeDOM → planner 的实际点云链保持不变。
4. 修改后只重采一次 Nodes-only 拓扑，要求本报告中的 4 个旧执行话题和 2 个辅助节点消失，且
   typed detections、单一 planner goal、`/detect/point_class` 与 `/Servo` 检查继续通过。
5. 因动作 1～3 改变正式 launch/运行注册面，再跑一次最终整场 Gate；无需重跑 ABCD 视觉矩阵。

另外，clean `catkin_make -j4` 暴露了 FAST_LIO/Livox 生成消息头依赖顺序问题；先串行生成消息后
再并行构建可以通过。这不影响本次拓扑结论，但实机部署前应在导航仓 CMake 中补齐 target
dependency，避免空构建目录下的偶发并行失败。
