## 本次新增核对

FreeDOM的visualize_static_pointcloud从static blocks中读取scan_in_subvoxel有效且dynamic_level为STATIC的扫描点，再交给SDF。阻挡点不是仅由顶棚或未知空间掩码直接填入；但标为STATIC不代表一定准确，仍可能存在错位、误分类或残留。因此不能未经溯源就按时间删掉静态障碍。

分别检查394.357s失败快照与484.400s后续快照；后者裁剪中心不同，超出快照范围的格明确记为未观测，没有把缺失格当自由空间。

## 为什么不能只放大半径

planner_execution.py对RETURN_HOME/ABORT按原始请求目标确认到达，这是防止门前后锚点被任意替代的现有约束。规划器即使找到约0.30m外的替代点，任务层仍可能等不到到达条件。只放宽距离又会改变门前后通过约束，不能照搬SEARCH的处理。

较合理的后续方向是将随机门引导的“允许到达区域”与感知得到的安全有效目标统一，同时保持通过面顺序、净空、航向及高度约束；或者先定位阻挡扫描点的生成/清理问题。前者需要跨规划与任务层回归，后者缺相应时段的原始点云/TF输入。当前证据不足以选定可靠的小补丁。

因此本轮结论是：**已尝试最小方案的离线筛选，未将无效或改变安全契约的参数调整提交为修复。** seed34已经实跑通过的等待上限候选保留；seed33维持原行为、原始FAIL记录及当前交付包不变，没有把“缩短超时更快ABORT”算成过门修复。
