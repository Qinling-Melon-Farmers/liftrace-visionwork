# 对准结束与释放结果乱序修复
## 原因
原仲裁器以当前commitment或已见start动作匹配回执。对准结束先清空commitment、随后start和success到达时两者都不认识，第一槽不能提交，第二槽许可被顺序门挡住。

## 修改
只有真正发布permitted许可才登记固定动作历史（任务/决策/尝试/槽位/目标ID/first_seen/类别及对准模式）。对准结束关闭继续许可且保留历史。start或有效terminal completed绑定真实执行编号；完成允许早于start，重复成功只推进一次。NOT_STARTED不占执行编号、不释放已锁槽；UNKNOWN保守锁槽但不抢占正事实编号。未授权/异身份/异执行编号拒绝，迟到结果不清除另一动作commitment。历史保留到当前仲裁器进程结束，不做会丢账的短时过期。

## 验证
生产方法调用覆盖全部start/end/success排列、实际publish路径、三槽连续推进、重复回执、拒绝与不明执行号不遮蔽正事实、未授权回执拒绝。相关165项通过；完整任务层505项（501通过4不适用跳过）。预展开两组42节点通过，五包Catkin构建通过。系统Python预展开遇到已有PyYAML异常，使用既有rl_drone做纯配置解析通过，未改飞行参数/安装依赖。

此修复不证明执行器实际释放载荷，也不替代板端验证。两个对照均包含本修复，仅高位续扫开关不同。
