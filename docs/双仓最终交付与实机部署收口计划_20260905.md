## 4. 最终交付工程包定义

### 4.1 源码权威

最终不是把两个仓库再次复制成一个大目录，而是三个固定 revision：

1. **视觉源码**：`liftrace-visionwork`，权威拥有 `camera_sdk`、`uav_vision`、板端 RKNN
   入口、相机内参/外参 profile 和视觉评测工具。
2. **导航控制源码**：`liftrace-controlwork`，权威拥有 `uav_mission`、Mission Manager、
   Planner Bridge、`patrol_control` external mode、FAST-LIO、FreeDOM 和 Fast-Planner。
3. **策略研究源码**：`liftrace-sim`，只输出候选策略和研究报告，不作为机载运行依赖。

两套飞行源码用一个 `integration_manifest.yaml` 绑定，至少记录：

```yaml
vision_revision: <merged visual main/tag>
navigation_revision: <merged navigation main/tag>
strategy_revision: <liftrace-sim revision used for candidate>
model_artifact: merged_standard_fp32.rknn
camera_intrinsics: calibration_1280x720.yaml
camera_extrinsic_profile: real_2026_ks2a543_body_runtime
mission_profile: r2026
search_policy_profile: <accepted candidate>
```

### 4.2 联合运行包

最终传给板端的是由上述 revision 构建出的一个运行包，而不是包含全部历史、日志和仿真资产的
仓库压缩包：

```text
liftrace_2026_runtime/
  integration_manifest.yaml
  vision_install/                 # camera_sdk + uav_vision + 消息/launch
  navigation_install/             # uav_mission + patrol_control + 定位/规划运行依赖
  models/merged_standard_fp32.rknn
  config/real/                    # 内参、单一 TF、任务和机构 profile
  scripts/start_bench.sh          # 默认不解锁、不起飞、不触发机构
  scripts/start_mission.sh        # 仅人工完成实机 Gate 后启用
  HANDOFF.md
```

构建顺序固定为：先构建并 source `vision_ws`，再构建导航工作区；运行时由同一个入口 source
两个 install space。模型不放入 Git，但必须在 manifest 中固定文件名、模型族和导出版本。
`uav_vision_eval`、Gazebo worlds、rosbag、日志、测试视频和轻量仓不进入实机运行包，另存为
验收证据包。

### 4.3 单一运行链

最终正式链只保留下列权威关系：

```text
camera_sdk -> uav_vision typed detections/targets
           -> Mission Manager (唯一搜索/选靶策略)
           -> NavigationDecision
           -> Planner Bridge (唯一 /fastplanner/goal 发布者)
           -> patrol_control external mode (轨迹跟随和末端控制)
           -> release arbiter -> guarded actuator proxy
           -> post-delivery route -> r41 已验证的 H 兼容适配 -> AUTO.LAND
```

- 保留已经在 r41 证明有效的 `NavigationDecision/NavigationResult`，不再叠加
  PlannerControl/Ack、epoch 或第二个 coordinator。
- 导航仓现有 `vision_ws/src/uav_vision` 副本不得成为运行时权威。最终 P3 先用联合构建和
  `rospack find uav_vision` 强制解析到视觉仓；物理删除副本要等 clean install 独立构建验证后
  另做，不在已通过链上临时制造包依赖变化。
- r41 中 `patrol_control` 仍直接订阅 `/detect/land_mark_point`，该话题由视觉
  `detect_compat_bridge` 从 `/uav_vision/detections_mapped` 的 `landing_pad` 生成。最终基线保留
  这一已验证 H 适配；typed H 直连及关闭宽口径兼容输出作为后续独立接口 Gate，不冒充已实现。
- 旧 `/Servo` 可以作为未改机构的底层 ABI 继续复用，但只能位于 guarded proxy 之后，不能
  重新获得任务或释放裁决权。

## 5. 坐标与外参收口

### 5.1 当前实现与目标权威树

机械组已确认相机可按正下方处理：距飞控盒 `0.16 m`，距 MID360 雷达 IMU `0.21 m`。但
`feat/vdeploy-camera-extrinsic@f0b1b8b` 当前运行 launch 实际发布的是
`body -> downward_camera_optical_frame`、平移 `[0,0,-0.16] m`；`-0.21 m` 仅记录在 profile
的测量元数据中。工程内尚未建立并验证可供该静态 TF 使用的命名 `mid360_imu` frame，因此不能把
下列目标树写成当前已生效事实：

```text
camera_init -> mid360_imu -> downward_camera_optical_frame
                              xyz = [0, 0, -0.21] m
```

Stage B 先以实际 TF 树决定唯一 parent。若 `mid360_imu` 已有稳定定义和与 `camera_init/body` 的
有效连接，再新增并启用 `mid360_imu -> camera` 的 `-0.21 m` profile；否则保留当前
`body -> camera` 的 `-0.16 m` provisional profile 并实测验证。不要同时发布两条能闭环到同一
camera frame 的静态 TF。水平偏移暂按 `[0,0]`，下视旋转使用 ROS optical frame 约定；投递机构
沿用 2025 的机构偏置，但放在独立 real payload profile，不能混进相机外参。

### 5.2 仿真与实机不得共用平移

r41 的 KS2A543 SDF 仍为相机相对 `iris::base_link` 下方 `0.05 m`，MID360 include 位于上方
`0.08 m`。它是 r41 的仿真几何证据，不能把 `-0.21` 直接覆盖进去，否则 revision 相同却世界
几何改变。

后续若追求更接近实装，新增明确的 `real_mount` SDF profile：先定义仿真 base 是否代表飞控
IMU，再按飞控到相机 `-0.16 m`、MID360 IMU 到相机 `-0.21 m` 成对设置雷达与相机 link。
旧 r41 SDF 保留作回归。`0.20→0.21 m` 的 1 cm 修正本身对 2.4 m 高度投影很小，真正高风险是
父 frame 选错、形成重复 TF 或只改 TF 不改 SDF。

## 8. 基线交付后的运动模糊与 MJPEG 专项

### 8.1 当前真实链事实

实机 `camera_sdk` 已向 UVC 请求 `MJPG 1280×720@30`。OpenCV/V4L2 在 `cap.read()` 时解码为
BGR，随后正式 RKNN 节点订阅 ROS `sensor_msgs/Image`。`/camera/image_raw/compressed` 是有
订阅者时才额外编码的调试/传输输出；检测器没有必要改为订阅 JPEG。仿真要模拟的是“相机端
MJPEG 压缩再解码后的像素退化”，而不是给导航或检测器再加一套 compressed 接口。

### 8.2 最小实现

本专项不进入首次最终 P3 Gate。后续在视觉评测包增加一个仿真专用 `camera_impairment`，放在
Gazebo camera 与现有视觉链之间：

```text
/downward_camera/image_raw
  -> camera_impairment(mode=off|mjpeg|motion_blur|combined)
  -> /uav_vision/sim_camera/image_raw
  -> 现有 detector/refiner/map/memory
```

- `off` 必须逐像素透传；默认仍为 off。
- `mjpeg` 对每帧执行 JPEG encode/decode，初值用当前 `jpeg_quality=80`；随后从实机 UVC 原始
  MJPEG 帧的量化表校准，不凭经验长期固定。
- `motion_blur` 使用曝光时间和相邻 pose 估算像素位移，生成方向性 PSF；先做
  `2/5/10 ms` 曝光档。没有实机曝光数据时必须标为 stress profile，不能称为实装真值。
- `combined` 固定顺序为先曝光积分、后 MJPEG 压缩，接近相机成像链。
- 输入/输出 `header.stamp` 和 frame_id 不变，CameraInfo 原样复用；处理 wall latency 单独记录。
- subscriber/publisher 均为 `queue_size=1`，不得积压；不修改视觉消息、导航消息或 detector
  内部模型接口。
- 由视觉仓提供一个测试 wrapper remap 图像话题，导航正式 launch 默认不依赖评测节点。

### 8.3 验收范围

先跑小矩阵，不重跑整套 ABCD：

- 五类目标在 `2.4 m / 1.0 m/s` 的基线、MJPEG、blur、combined 四档；
- C 中心/左右边界各一个条件；D 中直线、转弯和非零偏航各一个条件；
- H 首次识别、10 帧锁定和中心误差；
- 记录 P_confirm、P_selected、detector/pipeline P95、map error、JPEG 大小和丢帧。

只有 combined nominal 明显改变候选策略或 H/投递结果时才扩展边界测试。通过专项测试的候选
profile 进入后续版本的独立完整 Gate；stress profile 只作鲁棒性诊断，不阻塞无退化基线交付。
