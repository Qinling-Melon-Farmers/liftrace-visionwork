# 视觉工程精简与 B100 延迟复盘

更新时间：2026-09-04

## 1. 结论

B100 历史报告中的 `confirmation_processing P95=448.181 ms` 不是 YOLO 单模型的稳定推理
时延，也不是 OrangePi 实机性能。最终修复确认它是 recorder 图像与候选两个独立 subscriber
回调之间的排队诊断，语义上不能作为检测链起点。合同指标现统一为同一 source stamp 的
`detector callback start → recorder candidate receipt`；KS2A543 完整 B100 的该项 P95 为
`181.990 ms`，detector processing P95 为 `145.724 ms`。

当前不通过增加超时、重试、兼容 topic 或额外 manager 掩盖该问题。已完成的修复是缩小仿真
夹具、减少重复审计、精确配对检测帧 TF/时戳，并把 recorder 传输诊断、detector processing 与
same-host pipeline 分开报告。

## 3. 448 ms 的分层原因

### 3.1 首要原因：仿真源与宿主调度没有跑满

历史 B100 相机源只有约 9.95 FPS，recorder 实收约 8.49 FPS；模型离开 Gazebo 后在同一 RTX
4060 Laptop GPU 上对 `real_target.mp4` 的 100 帧复跑，推理/总耗时 P95 仅
15.13/15.23 ms。GPU 观测约 29%～45%、温度约 46°C，CPU 仍有约
66%～70% idle，内存/swap 无压力，也没有随 trial 推进持续恶化，故不符合显存泄漏、热降频或
模型算力饱和特征，更像 WSL/Gazebo/ROS 多进程唤醒和渲染同步造成的调度抖动。

### 3.2 历史相机夹具做了无用工作

旧 `vision_eval_camera` 引入完整 Astra D435i：彩色、双红外、深度均为 640×480@30，另有
100 Hz IMU；V-SIM-04 只订阅彩色流。改成单彩色后，代表 10 格 detector processing P95 从
92.12 ms 降到 68.84 ms，说明未用传感器渲染是可复现的成本之一，但不是全部 448 ms。

### 3.3 `confirmation_processing_ms` 混入 recorder 排队

该指标是“recorder 收到候选的 monotonic 时刻”减“recorder 收到同 source stamp 图像的
monotonic 时刻”。图像和候选走不同 ROS subscriber，两个回调的排队顺序不属于检测算法。
完整 D435i 10 格中有一格 process 为 350.5 ms，而同格从 detector callback start 计算的
pipeline 只有 80.5 ms；KS2A543 10 格又出现 2 个 source stamp 无法精确对表。这解释了为何
process 会被异常放大，也解释了它偶发缺样。

### 3.4 融合与审计放大压力

三条检测分支速度不同，fusion 在 0.8 s 后仍会发布 partial bucket，随后正式 target memory
再拒绝它。历史 B100 有大量 partial/incomplete 路径，同时 recorder 对粘性 CONFIRMED 的每次
重复发布都写审计事件：约 55,585 条 confirmed、5,473 条 selected，`events.csv` 约 24 MB。
这些行为不直接等于 448 ms，但在单机长矩阵中增加 Python 回调、序列化与磁盘写入竞争。

## 4. 过度设计/过度防御复盘

| 内容 | 判断 | 后续动作 |
| --- | --- | --- |
| 模型路径/profile fail-fast、TF/地图/年龄门禁、r2026 禁选 tank、释放许可、单 planner goal publisher | 必要安全边界 | 保留，不为“精简”移除 |
| `navigation_search_delivery_vcl06.launch` 的单 manager + 单 execution bridge | 正式主线 | 只在此入口继续开发 |
| `coverage_search_manager`、`external_candidate_manager`、`target_search_manager_py` + `navigation_visual_delivery_adapter` | 已完成阶段验证的历史链 | 冻结为 regression-only；不得继续补正式策略或新接口 |
| D435i/KS2A543 多 profile 动态选择 | 会形成长期兼容负担 | 不做；当前默认使用实装相机，历史夹具由 Git revision 复现 |
| fusion 先发布 partial、正式 memory 再拒绝 | 诊断与生产路径重复 | 本轮先不改消息；下一小步让 formal memory 不消费 partial，评测器仍可计数 |
| 每帧重复记录粘性 CONFIRMED/selected | 证据量远超业务信息量 | 按 trial + event kind + stable ID + last_seen 去重，保留状态迁移和 profile 违规 |
| recorder process 与 same-host pipeline 两套“确认时延” | 独立订阅者收图不是检测链的可靠起点 | 合同版本化改用同 source stamp 的 detector callback-start→候选 receipt；旧 process 只作可选传输诊断，不增加新字段 |
| 大量有界握手、产物完整性检查 | 仅评测层合理 | 保持在 `uav_vision_eval`，禁止复制到生产 manager/adapter |
| 旧 `/detect/*` 兼容桥 | 2025 `patrol_control` 尚需 | 只在旧链显式启用；新板端与 VCL06 默认关闭，闭环替换后整体删除 |
| optional/strict 双行为继续扩展 | 容易堆叠状态分支 | 当前合同冻结；新增功能默认只服务 strict 正式链，不再为每个旧分支追加兼容语义 |

本轮没有顺手删除历史 manager，也没有给每个相机/旧链增加 profile selector。原因不是“永远
兼容”，而是删除跨组历史入口超出视觉侧权限；正确收敛方式是冻结、不再演进，待 VCL06 实跑
通过后由单独清理提交删除。

## 5. 已实施的最小修正与后续优先级

已实施：

- 本 feature 分支把 V-SIM-04 夹具从整套 D435i 改为单彩色 KS2A543；使用实装
  `1280x720@30`、标定视场/D、`/camera/*` 话题和 `downward_camera_optical_frame`。
- 不提供 D435i 运行兼容开关；历史结果继续绑定其原 revision。
- 工作树由 24 个收敛为 8 个：仅保留根工作区、当前视觉修复工作树和 6 个导航所有工作树；
  14 个 clean 视觉工作树及另外 2 个已归档证据的视觉工作树已安全移除，分支/提交未删除。

下一步按收益排序：

1. 先把当前相机外参按 `body(IMU) -> downward_camera_optical_frame` 实测并冻结；这是整机地图
   投影的真正阻塞。
2. fusion/recorder 做一次小范围“partial 不入正式 memory + 终态事件去重”，不新增 topic。
3. 已完成 KS2A543 A25/B100/C25/D11；后续只在整机负载下复核 D11 的 265.2 ms pipeline 和
   最终候选工作点，不再重复整张单 seed 曲面。
4. 最后才清除冻结旧 manager；必须由 VCL06 正式链 Gate 和人工合并确认驱动，不能边联调边删。

本轮评测有效性和 A/B/C/D 当前可执行范围已经关闭；是否 MR 到 main 仍按分支 Gate、干净工作树
和人工合并确认执行，不由单次 visual-only 高分自动决定。
