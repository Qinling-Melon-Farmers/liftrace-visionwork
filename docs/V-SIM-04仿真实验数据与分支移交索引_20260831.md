## 8. 为什么当前不能直接合 main，以及如何 MR

结论是：**可以现在开 Draft PR/MR 做审查，不能现在点击合并。** GitHub 对应术语是 PR。

最顶层 execution 当前不能直接合 main 的工程原因：

1. 它一次带入 V-CL-05、V-SIM-04、导航合同、执行 bridge、相机与地图相关的 111 个提交，
   不适合作为一个未经分层验收的黑盒大合并；
2. 最新联合 Gate 明确 `FAIL/map_missing`，真实 `P_interrupt`、90 秒同 ID 链和 600 秒三投均
   未成立；
3. 返航、H 降落和地图 A/B 推广条件没有关闭；
4. lidar 与 execution worktree 都存在未提交且重叠的 `mid360_sim.yaml` 修改，真实地图修复
   还不在 Git 历史中；
5. `main` 规则要求一个 Gate 一个可审分支、实跑 PASS、工作树干净并以 no-ff/PR 合入。

推荐把“可 review”和“可合 main”分开：

1. 现在可以为现有远程层级开 Draft stacked PR，目标依次设为其父分支：
   `navigation → vcl05`、`performance → navigation`、`next → performance`、
   `execution → next`。这样能立即 review 每层增量，不必等待最终 Gate，也不新增接口分支。
2. `vcl05-full-random-deploy → main` 只有补齐自身完成定义和 Gate 后才合。
3. 若严格拆 Gate，应先把 local `vsim04-stability@0deeb1e` push 成独立 PR；否则它会随
   navigation PR 一起被审查，需在 PR 描述中明确这 5 个视觉基线提交。
4. 父层合入 main 后，逐层把下一 PR retarget 到 main；performance 是唯一 V-SIM 汇总 PR，
   不再为 pillbox/redcross/repeat/soak 等历史 worktree 重开 PR。
5. 三个 VCL06 小接口分支已经被 next 吸收。为避免接口和兼容层继续膨胀，优先审
   `vcl06-next-integration` 的整合增量，不再为旧版本重复开 MR。
6. 真实地图修复应先在准确命名的小分支提交并验证地图持续新鲜，再合入 execution。
7. 最终 execution 只有在干净 post-fix 90 秒同 ID 链、A/B 安全条件、600 秒三槽返航/H
   落地 Gate 全部满足后，才合入 main。

如果目标只是让团队现在看到 diff，开 Draft PR 即可；如果目标是更新验收基线，则必须先完成
上述 Gate。二者此前被口头统称为“MR”，是造成“好像不能 MR”的主要误解。

   同时继续改 `mid360_sim.yaml`；

   不先机械补满剩余 62 个 B 矩阵格；
5. 90 秒通过后再排 600 秒三投、返航和 H 落地 Gate；
