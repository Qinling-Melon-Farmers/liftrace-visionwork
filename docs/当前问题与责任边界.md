当前运行边界：完整视觉 ROS 链、Gazebo 定量场景和飞行联调在笔记本完成；OrangePi 已有
统一六分类 FP32 RKNN 离线图片/视频和短时相机烟测，但尚未完成 ROS CameraInfo/TF 与
10 min 稳定性。离线板端结果不能写成机载闭环结果。

## 1. 视觉组必须解决

### 观测契约

- 源图像时间戳、CameraInfo、camera frame 和 TF 的合法性；
- 输出保留源时间，不能用转发回调时间伪装新观测；
- 明确像素中心、精修中心、地图点、中心来源和拒绝原因。

### 检测与实例

- 五类标准目标与 `red_cross` 的粗发现；
- `red_cross` 几何复核；
- 蓝色圆环检出和类别—圆环实例关联；
- H 外圈与内部 H 结构联合确认；
- 普通黑圈、残圈、墙体/地面纹理等负样本误报控制。

### 地图与记忆

- CameraInfo + TF 地面投影精度；
- stable ID、跨视角去重、reset；
- 长期地图记忆与当前 `last_seen` 新鲜观测分开；
- 过期候选不得因 topic 重发重新获得控制资格。
- 同一物理地图目标不得因单帧类别抖动拆成多个 ID；确认和切类均需连续帧与置信度门槛；

### 末端视觉证据

- 对准偏差、稳定时长、目标身份、关联、位姿质量；
- 按 `SEARCH/APPROACH/DROP_ALIGN/LAND_CONFIRM` 门控观测；
- 发布结构化 `release_evidence` 和拒绝原因；
- 保持旧 `drop_ready` 兼容，但明确它不是最终许可。

### 测试与部署

- L0 mock assertion；
- Gazebo 独立真值、固定 seed、自动 recorder/report；
- headless shadow 飞行；
- 实拍回放域差；
- RKNN 数值一致性与 OrangePi 性能/稳定性。

## 2. 控制/规划组负责

- 全场覆盖搜索、搜索航线、候选接近和恢复搜索；
- 何时允许视觉中断当前任务；
- 统一位姿源和坐标系；
- 局部规划、避障、门区通过和轨迹执行；
- 剩余时间/电量调度；
- 最终 `release_permission`、舵机动作和降落安全互锁；
- 删除“超时即投递”或“超时即确认 H”等危险控制语义。

视觉组可以定义接口和提供验证场景，但不在 `uav_vision` 中实现这些控制业务。

## 3. 共同负责的接口

| 接口问题 | 视觉侧 | 控制/任务侧 |
| --- | --- | --- |
| 任务阶段 | 只消费并按阶段过滤 | 发布唯一权威阶段 |
| 候选目标 | 发布 stable ID、位置、质量、年龄 | 决定接近/忽略/恢复搜索 |
| 位姿有效性 | 检查 TF、时间和投影质量 | 提供唯一可信 pose/TF |
| 对准 | 输出偏差和稳定证据 | 产生运动指令并限制速度/高度 |
| 释放 | 发布视觉证据 | 组合飞行/机构/规则状态形成许可 |
| reset | 清空/冻结相应记忆 | 在任务边界调用并确认 |

共同接口必须有确定性 mock、超时、乱序、TF 缺失和旧观测重发测试。

## 4. 当前最危险的误解

- `selected_target` 刚收到，不代表目标刚被看到；
- `map_valid=true` 不代表地图点误差已经合格；
- `drop_ready=true` 不代表允许执行机构动作；
- H 外圈被检测到，不代表 H 结构已确认；
- 固定航点看到所有靶，不代表具备全场自主搜索；
- 新视觉 GUI 仿真有输出，不代表算法召回率、中心误差或地图误差达标；
- 旧控制链完整跑完，不代表 2026 视觉业务闭环完成。
- 实拍回放中类别—圆环“自洽关联率”不等于有人工真值的关联召回率；
- ONNX 能被 Runtime 加载不等于与 PyTorch 数值一致，更不等于 RKNN 已可上板；
- 仓库中存在 `phase_d_board.launch` 不等于 OrangePi 已经运行或达到实时性能。

## 5. 当前非视觉阻塞项的处理原则

按《基地无人机备赛流程(1).pdf》官方分工为三组：飞控组（硬件/结构/PX4 调参/飞手）、
导航组（机载 SLAM、路径规划、流程控制、仿真环境、精准降落）、识别组（检测/圆心/框
识别/训练/香橙派 RKNN 部署）。本文档所称"控制/规划组"=导航组、"视觉组"=识别组；
比赛假设 8.20 举行，实机部署与组间联调窗口极短。

- FAST-LIO、Fast-Planner 当前不替换（导航组资产，识别组只消费位姿/TF）；
- Fast-Planner 稳定性（低空下降速率慢、端点/返航可达性波动）由导航组处理；
- 原 2025 链当前已完成自动起飞和三次软件 mock 投递，但原始 0.8 m 门洞穿越、北区巡航、
  返航和降落尚未完成；这属于控制/规划/仿真载体前置，不计入视觉算法完成度；
- 当前默认 `toudi4_copy.world` 缺少旧门洞 `Wall_15` 和北区侧墙 `Wall_16`，
  必须先建立保留 toudi4 靶标/H 的专用 corridor 派生 world；在缺失障碍的空场跑通旧坐标无验收价值；
- H 模型存在不等于 H 降落通过。必须同时记录 landing 阶段、H 内外结构证据、降落许可和最终落地；
- `flag_planner_px4=true` 是直接 MAVROS 航点模式。该模式即使通过门洞，也只能证明预设路径
  可执行，不能证明 Fast-Planner 在线避障；
- 最新 `No Effective Points!` 只证明 FAST-LIO 当前观测退化；在直达模式下，不能直接推导
  它是飞机穿门失败的唯一根因。PX4 实际估计器输入、TF 和点云必须分层取证；
- 视觉评测优先使用确定性 mock、Gazebo ground truth 和 shadow 航线，不等待自主搜索完成；
- 如果位姿/TF 不可靠，视觉报告应把样本标为 `pose_invalid`，而不是用错误地图点继续评分。

## 6. 交付边界

视觉组交付的是“可复现的观测与证据”：代码、参数、消息契约、固定场景、真值、逐样本指标、回放和板端性能。最终比赛闭环由任务、规划、控制和执行机构共同完成，任何一组都不能用另一组尚未完成来掩盖自己接口无证据的问题。
